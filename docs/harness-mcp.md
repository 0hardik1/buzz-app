# Harness MCP servers

Each harness has its own default for the MCP servers in its configuration. Codex and Claude Code both load the servers their configuration turns on, except for a protected agent, which loads none. One optional plugin may override that default for an agent. With no such plugin enabled, each harness uses that default directly; a launch waits only while Buzz reads its plugin settings. When the owner disables or removes that plugin, each harness's default applies again, including to servers the plugin had turned off.

## Plugin API

A plugin declares `host.agentMcp: true` in its manifest. Installation review tells the owner: "Choose which of your harnesses' MCP servers your agents load, including servers Buzz leaves off. Can start a configured server to list its tools. Cannot add servers or call their tools." The grant cannot add a server, call one or see its calls. A plugin that checks calls before they run does so through agent hooks (`host.agentHooks`, [agent tool hooks](agent-tool-hooks.md)), which the owner reviews separately. Listing a server's tools (`inspectHarnessMcp`) starts that server if it is not running. The review's details add: "Only one plugin controls this at a time: the first one to start. When it stops, another plugin with this access can take over."

- `ctx.agents.controlHarnessMcp({ choose(agent) })` registers the one control. The first plugin to register holds it; the owner does not pick which plugin that is. A second registration throws. The control ends with the plugin's scope, and then any other running plugin with the grant can register. Any plugin with the grant can call `harnessMcp` and `inspectHarnessMcp`, whether or not it holds the control.
- `choose` returns an object of overrides by server name: `false` is off, `true` is on, and `{ off, known }` is on without the `off` tools. `known` is every tool the plugin knows the server has, for a harness that can only name the tools it allows. A name left out keeps the harness's default, and `undefined` leaves every name out. So a server added to the harness's configuration after the plugin's last report keeps the harness's default until the plugin learns its name from `loaded` or a new report. Any other value for a name means off; an answer that is not a plain object means no server. The control is asked only while its plugin is running.
- The control may also have `loaded(agent, servers)`. After a session of an unprotected agent passes the read-back below, core calls it with what the session listed: each server's `name`, and its `state` and `tools` (each a `name` and an optional `description`) where the harness lists them. The call comes after the session goes on and only while the control's plugin is running; its throw or rejection is ignored. Core keeps none of it, so a plugin that wants a server's tools later keeps them itself.
- `ctx.agents.harnessMcp(agentKey)` returns what the agent's type reports: `tools` (whether single tools can be left out), `inspect` (whether `inspectHarnessMcp` works), `calls: true` when the type's agent hooks see this agent's native MCP calls before they run, so a plugin's hook can stop one (kept only when exactly `true`, never for a protected agent; without it a call the choice allows runs unasked), and `servers` (`name`, `default`, an optional `state`, and an optional `reason`: the harness's own words for why it can't load the server). It is `undefined` when the type does not report, including a type with no MCP client, which declares `harnessMcp: { client: false }` in `ctx.agents.types()`: it loads no server, so there is nothing to choose. A plugin can give its agents tools of its own with `addTool`'s `when` instead.
- `ctx.agents.inspectHarnessMcp(agentKey, server)` lists one server's tools without a model turn. Core keeps nothing. It rejects protected agents, and the harness rejects a name it does not configure.

## What core keeps

- A protected agent loads no native MCP server, and the control is not asked.
- A control that throws means no server for that launch.
- A plugin that declares `host.agentMcp`, is enabled, and is not yet running holds a launch until plugin startup settles, for at most 30 seconds. If it is still not running, the launch loads no server. Until the plugin settings are read, any enabled plugin may declare it: a launch waits while Buzz reads them, and loads no server if they need a reset. One the settings keep from running (a catalog error, paused external plugins) counts as not running. Core reads this from `pluginStatus.unavailable("agentMcp")`, which answers the same for any manifest access.
- After the harness starts a session and before its first prompt, the adapter passes what the harness lists as loaded, with the answer `choice` gave that session, to `agents.harness.mcp.started`. Only the plugin that registered the agent's type can call `choice` or `started`, and only for an agent running here. Core reads the agent and its protection from what runs, not from the caller. It throws when a server or tool that was turned off is listed (for a protected agent, any server), and the launch stops. This read-back catches a server after the harness started it; it does not prevent the start. The session cannot use it.

## Calls

Core does not check MCP calls. A plugin that approves or blocks calls registers agent hooks for the harnesses it checks; each adapter documents the events, and Codex's MCP tool events name the raw server and tool ([agent tool hooks](agent-tool-hooks.md)). Hook callbacks get `direct` and `conversation` for the turn core delivered.

Such a check is only as strong as the harness's hooks. Codex runs a call when its hook errors or runs past its limit, and a thread its bridge does not serve has no hooks; the plugin's own post-call hook is the backstop. Codex asks `choice` again for each thread, so a changed choice, or a control plugin that stopped, applies from the next turn; calls already in the current turn run without the stopped plugin's hooks.

## Adapters

A type declares `harnessMcp: { report(agent), inspect?(agent, server) }`, or `harnessMcp: { client: false }` when its harness has no MCP client (Pi). `report` names servers from the harness's own configuration without starting any. An adapter asks `agents.harness.mcp.choice(agent)` when it launches a session and applies the answer; execution targets report and apply nothing, so a session there loads what the remote host's configuration turns on.

### Codex

- Names come from `config/read`. A server chosen on has no thread entry, so `config.toml` applies; with `{ off, known }` it gets `off` as `disabled_tools` (joined with its own). Codex can leave out single tools, so it ignores `known`. A server chosen off gets `enabled: false`. A name the choice leaves out has no entry, as with no choice, except for a protected agent, whose every server gets `enabled: false`. Buzz never sends `enabled: true` and never sends a name `config/read` does not list.
- A server with `enabled: false` is not started by Codex (checked against 0.164.0 and 0.167.2).
- The read-back calls `mcpServerStatus/list` once for each `config/read` name, with the thread's `threadId` and that `serverName`, which reads the thread's own connection. Without a `serverName`, or without a `threadId`, that call starts servers again, so Buzz never makes it that way. A name the choice leaves out follows `config.toml`, so it is not checked. With no choice Buzz makes no status call.
- Compaction resumes its thread with every server off, with or without a choice, and reads that back when a choice is in play.
- The report names servers only. The read-back passes each loaded server's state and tools, with descriptions, to `started`, so the control's `loaded` gets them. `inspect` runs an ephemeral thread with every other server `enabled: false` and `thread_unload_delay_secs: 0`, reads status for that `threadId`, then unsubscribes, so Codex unloads the thread and stops its server. No turn runs and nothing is saved.
- `state` is `disabled` only when `config/read` shows `enabled = false`; a server Buzz turned off in a thread has no state.
- The chat-title thread turns every listed server off by name.
- The report says `calls: true` while Codex hooks are on (`features.hooks`) and Buzz's hook bridge serves the agent's threads.
- MCP tool hook events carry the raw `mcp_server`, and `mcp_tool` when known, behind Codex's model-visible `mcp__<server>__<tool>` name. Buzz matches the name to the thread's server names and the tools its status listed; a name that matches no single server carries neither. Buzz's own bridge server is never named.
